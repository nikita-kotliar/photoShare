## Архітектура і безпека

| ID | Рішення | Чому |
|---|---|---|
| D-01 | Сайт і API на одному домені, nginx пересилає `/api` на бекенд | cookie працюють без CORS-складнощів |
| D-03 | Роль і бан беремо з бази на кожному запиті, а не з токена | бан і нова роль діють одразу |
| D-04 | Кожен токен має `jti`, після виходу він потрапляє в blacklist у PostgreSQL (D-05), прострочені записи чистяться | вихід справжній, без окремого Redis |
| D-06 | Усі помилки API однакові: `{ error: { code, message, fields } }` | один обробник на фронтенді, помилки під полями форм |
| D-15 | Невдалий запис у БД видаляє файл з Cloudinary; збій Cloudinary при видаленні світлини лише логується | у хмарі немає сміття, користувач не бачить чужих збоїв |
| D-22 | Оригінал у Cloudinary не змінюється, трансформація - це URL з параметрами в сталому порядку | однаковий набір - однаковий URL з кешу CDN; можна показати «до / після» |
| D-41 | Swagger описано в YAML, тест звіряє його зі списком маршрутів | документація не відстає від коду |
| D-43 | Розгорнуто на спільному сервері з HTTPS у підшляхах `/photoshare/` і `/photoshare-api/`, cookie `photoshare_token` з власним шляхом | новий піддомен недоступний; не заважаємо іншим сайтам на домені |
| D-47 | Пошук - параметризований SQL з індексами; тести на справжньому PostgreSQL | фільтри за рейтингом і тегами разом не вміщаються в `findMany` |
| D-10 | Міграції Prisma застосовуються при старті контейнера, перед ним - резервна копія бази | оновлення без ручних кроків і з можливістю відкату |
